# 第5层·主观输出 / 子位置：感觉

> 所属工作流步骤：第 5 步（顺序：第一层 → 第二层 → 第三层 → 第四层 → 第五层）
> 本子位置是独立可编辑模块，可单独编写，不依赖其他子位置文件。

## 本子位置定位
- **层**：第 5 层 · 主观输出
- **子位置**：感觉（sensation）
- **一句话说明**：观者看到设计的**第一秒即时感官印象**——美 / 酷 / 稳 / 轻 / 高级 / 温暖 / 尖锐 / 柔和。它是体验的入口，先于理性判断。
- **心智模型**：前面的 1~4 层是"你怎么造"，第 5 层是"别人怎么**感**"。感觉是设计落在感官上的**第一反应**，由第 2 层物料（颜色/质感/字型）+ 第 3 层形式（空间/构图/镜头）直接触发，**不靠文字解释**就能传递。感觉对了，后面的情绪和认同才有土壤。

## 在工作流中的位置（顺序执行 + 反推）
- **正向（验收）**：走完第 4 层后，用"第一眼感觉是什么"验收——若答不出或答偏，说明第 2/3 层没落实。
- **反向（反推 · 更关键）**：在定稿前就**先声明目标感觉**（如"要高级、要轻盈"），再把它翻译成第 2/3 层的可执行规格：高级→克制配色+大留白+细字重；轻盈→负空间+非对称+浅景深。感觉目标**先行**，向下反推。
- **上一步输入**：第 4 层「表达意图」（意图是准星，感觉是意图的感官落地）
- **本步要做**：明确"希望观者第一眼感到什么"，列出 2~3 个主感觉词，并确认它们由哪些物料/形式触发
- **输出给**：本层后续子位置（情绪、心理体验）；同时回灌第 2/3 层校验是否达标

## 操作要点

### 1. 感觉家族分类表（常见第一印象词）
| 感觉维度 | 典型词 | 通常由什么触发 |
|---|---|---|
| 美感类 | 美 / 高级 / 精致 / 粗糙 | 配色克制、留白、字重对比、材质精致度 |
| 温度类 | 温暖 / 冷峻 / 中性 | 色相（暖橙 vs 冷蓝）、光源方向 |
| 重量类 | 轻盈 / 厚重 / 稳 / 飘 | 负空间量、对称度、字体笔画粗细 |
| 态度类 | 酷 / 锋利 / 柔和 / 可爱 | 边角圆钝、撞色强度、图形几何感 |
| 时代类 | 复古 / 现代 / 未来 | 字体调性、质感工艺、配色饱和度 |

### 2. 四步定位法（定目标感觉）
1. **取意图锚点**：从「表达意图」拿主意图（如"情感·浪漫"），确定感觉基调。
2. **选 2~3 个主感觉词**：宁少勿多，超过 3 个就互相抵消（如"高级+轻盈+温暖"可行，"高级+可爱+硬核+复古"则乱）。
3. **映射触发源**：每个感觉词对应第 2/3 层的具体手段（见分类表右侧）。
4. **做第一眼测试**：遮住文字只看图，问"我第一眼感到___？"——若答非所问，回第 2/3 层修。

### 3. 维度五件套（感觉的验收坐标）
- **第一印象词**：能否用 1 个词概括？（美/酷/稳…）
- **温度**：暖 / 冷 / 中性
- **重量**：轻 / 重
- **精致度**：精致 / 粗粝
- **态度**：柔和 / 锋利 / 中性

### 4. 关键方法与注意
- **感觉先于解释**：好设计第一眼就"对味"，不需要读字。验收时先遮文字看图。
- **感觉词要可操作化**："要高级"必须落到"克制配色≤3色 + 大留白 + 细字重"，否则是空话。
- **不超过 3 个主感觉**：多感觉互相打架，观者无从记住。
- **感觉一致性检查**：第 2 层物料（颜色/质感）与第 3 层形式（空间/构图）必须**同向**触发同一感觉，否则"说高级却满屏撞色"自相矛盾。
- **承接意图、开启情绪**：感觉是情绪的输入——"轻盈"的感觉才会自然唤起"松弛/愉悦"的情绪（见本层「情绪」子位置）。
- **轻量 vs 商用**：个人/测试项目凭直觉定感觉即可；商用项目建议做小范围"第一眼联想"测试（问 3~5 人第一感，对齐目标）。

### 5. 上下层 / 同层衔接
- **← 第 4 层 表达意图**：意图是感觉的上位目标，感觉是意图的感官落地。
- **← 第 2 层 物料 / 第 3 层 形式**：感觉由它们直接触发，是验收它们的"体验尺"。
- **→ 本层 情绪 / 心理体验**：感觉是情绪的输入，情绪是心理体验的前奏。
- **↺ 反推回 第 2/3 层**：目标感觉未达成 → 回第 2 层调色/质、第 3 层调空间/构图。

## 备注
- 感觉 ≠ 情绪：感觉是第一秒的**感官印象**（美/酷），情绪是随之**唤起的状态**（喜悦/松弛）。一个是入口，一个是过程。
- 与「排版构图」备注呼应：构图气氛（呼吸感/张力）是感觉的主要制造者之一。

### 好看验收：三个物理动作（形式层，必做且先于技术校验）

> **技术校验只防硬伤，防不住"难看"**——溢出、字号、碰撞全过，东西依然可能平庸。完稿后**先做这三个动作**，再跑下面的技术校验。顺序不能反：先形式后硬伤，否则会陷入"一直在修溢出、从没看过整体"。

1. **缩略图测试**（缩到 25% 看）：还能立刻分辨出**主 / 次 / 辅**三级吗？分不出 = 层级对比不够，回去加大字号比或灰度差。
2. **眯眼测试**（眯眼或加 8px 高斯模糊）：画面应剩 **3–5 个视觉重量块**。少于 3 = 空散缺重心；多于 6 = 碎、无主次。
3. **倒转测试**（水平翻转或倒过来看）：**纯形式上的平衡是否还成立**？有没有偏向一侧？——这一招绕过"读内容"的习惯，专治"因为内容顺序对所以以为构图也对"的自欺。

> 三个动作全过，才算过了"好看"这一关。完整判据与修法见 `references/审美精度标准.md` **C 段**。

- [ ] **溢出**：任何文字/图块未超出画板边界或安全区？

## 补充 · 视觉验收的双评审闸门（builder 不能给自己打分）

> 通用验收机制（源自"参考图 → 程序化 3D 资产"类任务的质量闸门工作流，已去域化，适用于**任何有目标稿/参考稿的视觉产出**）。来源署名见 `references/来源署名/vinhhien112-img2obj.md`。

### 为什么需要：自欺是默认状态

自己做 → 自己看 → 自己判"挺像"，是 AI 做视觉的**默认失败路径**。builder 知道自己想做什么，于是自动把产出往意图上解释——**知道意图本身就会污染判断**。下面这套机制唯一的目的：让判断发生在**拿不到意图解释**的地方。

### 两个评审角色（各自独立子代理，互不通信）

**① 盲视觉 scout（只给图，不给解释）**

- **收到**：目标稿 / 当前产出 / 上一版（若有）/ 它们的**并排比对图**。
- **禁止收到**：意图卡、spec、组件 ID、参数、分数，以及 builder 的任何辩护性说明。
- **职责**：先做一遍"早期质量扫描"（前面的版本有没有明显缺陷），再审当前。输出**只给方向**——最多 7 条最高影响的问题方向，**不打分数、不给参数、不改任何东西**。
- 任何被禁内容泄漏给它 → 该次评审报 `UNVERIFIED`，**不算通过**。

**② 主独立评审（给完整信息，给精确修正）**

- **收到**：目标稿、当前产出与比对、完整 spec 与所有可编辑 ID（**不**给 builder 自提的分数）。
- **职责**：给一个复合相似度分（阈值自定），**并逐个审关键特征**，返回精确修正：精确对象 + 观察到的差异 + 期望结果 + 数值操作（设值/缩放/位移/旋转/替换）+ 参数路径与目标值 + **能证伪这条修正的证据**（哪个视图 / 什么条件下能看出对错）。

### 关键特征否决制（这套机制的硬核）

> **总分高，不能掩盖关键特征失败。**

放行需**同时**满足：复合分达标 **且** 每一个关键特征单独过闸 **且** 盲 scout 放行。**三者缺一不可。**

- **关键特征** = 少了它"就认不出是它"的那少数几个部件。3D 里是屋顶轮廓、轮毂、分叉点；平面设计里是 **logo 轮廓、主视觉主体、标题层级关系、品牌色落点、signature 元素**。
- 主审**不得**因为"当前阶段做得不错"就放行——只要还有明显的前期缺陷或关键特征失败，就不通过。
- 分数小幅下降**本身不是**否决理由；分数回退必须由并排视觉比对佐证。

### 冠军 / 挑战者（防止越改越糟）

- 首个有效产出版作为**冠军**。此后所有修改**只作用于挑战者**，冠军不动。
- 挑战者过闸才晋级为新冠军；失败则**事务性回滚**到冠军，挑战者留在审计历史里。
- **连续三次无实质改进 = 策略耗尽**：保留冠军，明确记一次「策略重置」，必须**换表示法 / 换路子**再试，不许在同一条路上继续磨。
- 证据 / 结构类失败**不消耗**质量尝试次数——它证明的是"做错了"，不是"做得更差了"。

### 编辑前的影响评估（先证明局部可恢复）

改之前先写一份，只有判定"局部可恢复"才动手：

| 字段 | 说明 |
|---|---|
| 目标对象 | 精确等于本次要改的东西，不多不少 |
| 受保护对象 | 邻近 / 已验收、**不得**被影响的部分 |
| 结构不变量 | 层级、比例、对齐、动效关系中必须存活的部分 |
| 预期效果 / 可能副作用 | 明说爆炸半径 |
| 下游影响 | 对**更晚阶段**的影响预测 + 现在已做的缓解 + 将来能验证它的检查 |
| 回滚点 | 回到哪个已知状态 |

会把不该动的结构一起改掉、或留下无缓解的下游风险 → **收窄或否决这批修改**，先别动手。

### 明确禁止

- **禁止用量化分数替代并排视觉比较**——相似度 / 美学分只证"来源与一致性"，不证"质量"。视觉回归只能从**目标稿 / 当前 / 上一版的图像比较**判定。
- **禁止把未观察到的东西当事实**——看不见的背面、被遮挡的结构、推测的尺寸，一律记为「有界假设」或「已知风险」，不许写成观察结论。
- **禁止在当前阶段做后续阶段的工作**——先收敛轮廓再谈细节；顺序反了会一直返工。
- **禁止用信心代替执行**——该跑的检查跑不了，就明说缺什么证据、把结果报 `UNVERIFIED`，不许声称完成。

### 如何实跑这套闸门（工具链 + prompt 要点）

**① 准备三张不可变证据图**

| 图 | 怎么来 |
|---|---|
| `source`（目标稿） | 参考图原图 |
| `current`（当前产出） | 网页产出用 `agent-browser open file://<绝对路径>` + `screenshot --full` 截图；本地 file:// 可行，不必起服务 |
| `comparison`（并排） | Python + PIL 合成：两图等高对齐、间隔 32–40px、加 `SOURCE` / `CURRENT` 中性标签（**只标身份，不标意图**） |

> **⏱ 省流截图 SOP（先看这段：截图是整轮闸门最慢、最容易拖垮节奏的环节）**
>
> 实测教训：无头浏览器（agent-browser）每冷启动一次吃 15–40s；更糟的是 `close` 若没杀干净，无头实例会**堆积、互相抢 CPU/内存**，导致越跑越慢、单次卡到分钟级。按下述做，可将截图自检压到几十秒：
>
> 1. **先静态自检，能不开浏览器就不开**：用 `Read`/`Grep` 核 HTML 结构、资源路径、字体 fallback；用 Python 像素测量（按背景色阈值算 bbox / 留白 / 中心偏移，即 `vmap` 思路）核构图。这一步秒级，能拦掉 80% 明显错误。
> 2. **截图前先锁命令**：跑一次 `agent-browser --help`（或沿用已验证模板）把参数定死——`open file://<绝对路径>` + `screenshot --full` 还是 `--output <path>`，**不要边试边跑**。
> 3. **单次截图 + 关闭校验**：`open → 等渲染 → screenshot → close`，然后**立刻 `tasklist` 查该无头实例（带 WorkBuddy `app-id` / `--headless`）是否真退了**；没退就 `taskkill /F /PID <pid>` 补一刀，杜绝堆积。
> 4. **基于那一张图精修**：拿唯一一张截图改 HTML；确需再截也严格限制 ≤2 轮，每轮都走第 3 步关闭校验。
>
> **进程清理安全红线（已踩坑）**：清理残留 chrome 时，**绝不用** `taskkill /F /IM chrome.exe`——会误杀你正在用的 Chrome 标签。用 `tasklist` 鉴别，只杀明确的无头实例（命令行含 WorkBuddy `app-id` 或 `--headless`）；若某进程树里混入了带 `User Data`（即你正常 Chrome）的进程，**立刻停手、不要 `taskkill /T` 连根拔**，避免误关。agent-browser 走"守护进程 + 自动重生"模式，反复 open/close 不干净就会越积越多。

**② 派两个子代理并发审（同一条消息发出，各自独立上下文）**

- **盲 scout 的 prompt 必须写明**：只给三张图的路径 + 当前阶段名 + 该阶段 rubric；**明令"你不会被告知这是什么、brief 是什么、改了什么，不要猜测意图"**；输出限 7 条、禁打分、禁给参数；**加一句"若看不到图像就输出 `CANNOT_PERCEIVE_IMAGES` 并停止，不要编造"**。
- **主审的 prompt 要给**：三张图 + 完整 spec + 关键特征清单（K1…Kn）+ 可编辑元素 ID 列表 + 迭代史；**明确扣下设计者自提的分数**；同样加"看不到就停"的兜底。
- 两者**互不告知对方结论**。

**③ 迭代**：汇总 → 只改挑战者 → 重渲染 → 重合成 → 重审。分数轨迹应可见地爬升；连续三轮无实质改进即换表示法。

**④ 已验证的经验（2026-08-31 三轮实战）**

- 子代理**确实能看图**，产出具体到"哪块区域、什么毛病、往哪改"。
- 闸门抓到过设计者完全没发现的硬 bug：signature 元素被 `overflow:hidden` 裁掉、实际根本不存在。这正是"builder 不能给自己打分"的价值所在。
- **评审结果本身也要核实**：本轮 scout 报告"SOURCE 的水印残留到 CURRENT"，程序化验证（对比亮像素占比）证明——水印在 SOURCE 属实（5.06% vs 对照 0.00%），但**没有**残留到 CURRENT（0.00%）。**scout 会误报"是否残留"这类跨图推断**，落地前用程序核一遍。
- 判据不要只看总分：本轮 K 特征逐个过闸才是把分数从 0.52 推到 0.78 的抓手（每轮都是靠明确的 K 失败项驱动修正）。
